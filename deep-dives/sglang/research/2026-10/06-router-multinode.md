## Mental models

1. **The gateway remembers where it sent text; it never asks a worker what it cached.** `cache_aware` keeps one radix tree of raw prompt characters per worker pool, tags nodes with the workers that received them, and counts load as its own open requests. Predicts: no tokenizer needed, works over plain HTTP, blind to evictions inside the worker and to traffic from other gateway replicas (unless `--enable-mesh`). Rows B3, B5, B7, D10, E4.
2. **Balance first, then affinity.** Every request first checks whether the fleet is lopsided (more than 64 requests apart and more than 1.5x); only a balanced fleet gets prefix affinity, and a weak match (30% or less of the prompt) also goes to the least-loaded worker. Predicts: under a burst, cache hits drop by design before any worker overloads. Rows B3, B4, B8.
3. **One request, two legs, one room id.** In PD mode the gateway turns a request into a prefill call and a decode call fired together, stamped with the prefill server's bootstrap address and a random room; the KV moves worker to worker, and the client sees the decode stream. Rows C1-C5, 05 C4-C6.
4. **Two codebases, one lineage.** SGLang's in-tree gateway (0.3.2) and the external SMG (1.13.0) come from the same `sgl-router` history; `pip install sglang-router` gives a January 2026 build of the first, `pip install smg` gives the second, and the v0.5.22 Docker image carries the in-tree build of the tag. Rows A1-A8.
5. **Cache-aware routing in the cluster tracks the engine's own events.** The experimental `sgl-router`, llm-d and Dynamo all subscribe to the ZMQ KV-event stream that `--kv-events-config` turns on; the shipping gateway does not. Rows E2-E4, F6, F10, G2.

## Where SGLang differs from vLLM (routing and orchestration)

- **A router in the engine repo, cache-aware by default.** SGLang tags and dockerises `sgl-model-gateway` with `cache_aware` as default; vLLM's routers are separate projects (production-stack `vllm_router`, chart default `roundrobin`; `vllm-project/router`, a fork of SGLang Model Gateway). vLLM dive section "16. Kubernetes: Production-Stack & Router". Rows G1, G3.
- **History-based affinity versus event-based affinity.** The SGLang gateway's default matches on routed prompt text, like production-stack `prefixaware`; precise, event-driven routing comes from the experimental `sgl-router`, llm-d or Dynamo for both engines. vLLM dive sections 16 and "17. Kubernetes: llm-d, KServe & Gateway API". Row G2.
- **PD pairing built into the router.** The SGLang gateway pairs and dual-dispatches itself; vLLM relies on a proxy or llm-d's sidecar. vLLM dive section "10. Disaggregated Prefill / Decode". Row G4 (and 05 F2-F3).
- **Orchestrators track SGLang more closely.** llm-d v1.0.0 installs SGLang v0.5.22; Dynamo v1.6.0 trails by one (0.5.21); Ray pins none; KServe's release has no SGLang runtime. vLLM dive sections "15. Orchestration: Ray & Ray Serve LLM" and "18. NVIDIA Dynamo & the Ecosystem" record a larger lag for vLLM, which the newest llm-d and Dynamo releases have since closed. Rows F13, G5.
- **Ray is a side door for SGLang.** Ray Serve LLM defaults to vLLM; SGLang enters through `server_cls=SGLangServer` over SGLang's own `RayEngine`, marked early development. vLLM dive section 15. Row G6.
