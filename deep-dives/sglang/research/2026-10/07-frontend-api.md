## Mental models

1. **An SGLang program is a client, and `fork` is a cache hint.** The frontend keeps no KV. Every `gen` resends the whole text so far to `/generate`; `fork` first sends the shared prefix as a zero-token request so the radix tree holds it, then each branch's request matches that node and adds a leaf. The program's fork tree becomes a branch point in the radix tree. (A7, A8, A9, A10; register 02 B5, B7)
2. **`select` is scoring, not sampling.** It sends every "prompt + choice" string in one batched zero-token request and picks the best mean logprob; the shared prompt is prefilled once thanks to the radix cache. (A12, A13)
3. **One engine, many dialects.** `/generate`, OpenAI chat and completions, Responses, Anthropic Messages, Ollama and `sgl.Engine` all end in the same `TokenizerManager.generate_request`; the dialects differ in defaults (max tokens 128 / 16 / context limit; generation-config sampling only on chat and Responses) and in which fields they read, not in the engine they reach. (B1, B4, B5, B19, C17, C18, D2)
4. **The admin plane is on by default and guarded by whichever key you set.** Weight updates, memory release, pause, flush and LoRA loading are always registered; with no key they are open, with only `--api-key` the inference key unlocks them, and only `--admin-api-key` separates operators from clients. (B10 to B14)
5. **A refit is a bracket: pause, begin, buckets, end, continue.** Updates write checkpoint-format values; `end_weight_update` converts layouts once; the radix cache is flushed so no request reuses old-policy KV. (B9, B11, D4, D5)

## Where SGLang differs from vLLM (design choices)

- **Native API first.** SGLang's always-on `/generate` takes text or tokens and is what its frontend, router and RL integrations speak; vLLM's token-in `/inference/v1/generate` is opt-in. vLLM side: "12. The OpenAI-Compatible Server". (G1)
- **A programming frontend.** SGLang still ships `sglang.lang`, built on prefix hints and logprob scoring; it is maintained but not the main interface at v0.5.22. No vLLM counterpart in sections 12 or 13. (G2, A21)
- **Admin plane always present.** SGLang registers RL and operations routes on every server and offers a second key; vLLM gates them behind `VLLM_SERVER_DEV_MODE=1` with no key. vLLM side: section 12. (G3)
- **Dialects.** Both serve Anthropic Messages; SGLang adds Ollama. vLLM side: section 12. (G4)
- **Tool calling flags.** SGLang needs only `--tool-call-parser` (or `auto`); vLLM also needs `--enable-auto-tool-choice`. vLLM side: section 12. (G5)
- **LoRA defaults and selection.** SGLang batches up to 8 adapters by default and selects an adapter with `model: "base:adapter"`; vLLM defaults to 1 adapter and rank 16 and selects by bare adapter name. Runtime loading is always available on SGLang, env-gated on vLLM, which also has resolver plugins. vLLM side: "13. LoRA & Multi-Adapter Serving". (G7, G8, G9)
- **Same design:** per-adapter prefix-cache namespaces (G10); in-memory, non-evicting Responses storage behind an opt-in (G6).
