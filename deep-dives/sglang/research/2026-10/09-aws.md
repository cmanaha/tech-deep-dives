## Mental models

1. **SGLang already speaks SageMaker; what varies is the entrypoint.** Every SGLang server registers `GET /ping` and `POST /invocations` (A1). The images differ only in how they turn environment variables into flags: `SM_SGLANG_` in SGLang's script and the AWS DLC, `SGLANG_` in ml-container-creator, with different boolean handling (A9, A10, F11). Prediction: a SageMaker failure with a working image is almost always a flag translation, an `--api-key` that blocks `/ping` (A5), or a host AMI whose driver predates CUDA 13 (A12, C8).
2. **`/ping` answers "has the model loaded", nothing more.** It is a static 200 that only exists once weights are loaded and graphs captured (A3, A4). Load time spends SageMaker's startup window; liveness after that needs `/health` or `/health_generate`, which do report 503 and can run a one-token generation (B5). Kubernetes probes and the AWS Beam sample use `/health` (B4, F1).
3. **On EFA, KV transfer and MoE all-to-all are two separate problems with separate libraries.** KV moves through libfabric (Mooncake's EFA wheel or NIXL `LIBFABRIC`) (D1 to D4). Expert all-to-all moves through NCCL GIN and aws-ofi-nccl (DeepEP V2 from AWS's fork) or NVSHMEM's libfabric transport (patched DeepEP V1) (D6 to D11). NIXL reaches EFA for KV and not for EP (D12). Prediction: an image can be ready for PD over EFA and still unable to run wide EP over EFA, and the reverse.
4. **The GPU generation sets SGLang's defaults; the EC2 family name is a proxy for compute capability and memory.** SM90 against SM100 changes the attention backend and the KV page from 1 to 64 tokens (C4, C5); memory tiers set chunk size and decode graph size (C6); SM80/SM86 run FP8 weight-only (C7). Moving a model from P5 to P6 changes prefix-cache granularity without any flag change.
5. **AWS's two SGLang image lines trade freshness for features.** The Ubuntu line is upstream plus the EFA installer and lands within about a day of a release (A13, A14). The AL2023 "server" line carries DeepEP V2 over EFA but runs SGLang 0.5.19, compiles its own kernels for SM90/SM100/SM103 only, and is amd64 only (D6, C9, C10).

## Where SGLang differs from vLLM

- **"25. vLLM on SageMaker & vs Bedrock"**: read the platform material (endpoint types, autoscaling metrics, Bedrock trade-off) as-is. Differences: SGLang's `/ping` is GET only and a static 200 (A3, A6); its `/invocations` accepts chat completions only and carries no SageMaker session handling (A2), where vLLM's in-tree `/invocations` is wrapped in SageMaker's stateful session manager and adapter injection (vLLM register S25); SGLang is absent from the LMI containers vLLM ships in (A18); HyperPod's built-in disaggregation is vLLM only (A21); SGLang's own SageMaker script mishandles booleans (A10).
- **"24. vLLM on Amazon EKS"**: EFA device plugin, hugepages, LWS and Karpenter read as-is (B2, B11). Differences: SGLang binds `127.0.0.1` by default (B8), uses `/dev/shm` for multimodal features and DP load snapshots beyond NCCL (B3), and its probes should target `/health` or `/health_generate` with the generation semantics in B5.
- **"23. EC2 Topology & Placement Groups"**: reads as-is; the topology and placement facts in D18 are engine-neutral.
- **"22. vLLM on AWS GPUs, EFA & NIXL"**: the NIXL `LIBFABRIC` route and the EFA installer facts carry over (D2, D3, D17). Differences: SGLang adds a second KV route, Mooncake's EFA wheel with its allocator guard (D1); SGLang's EP over EFA runs through DeepEP V2 with AWS's fork, packaged in an AWS SGLang DLC (D6 to D8), and SGLang's NIXL EP backend has no EFA path (D12). The instance-family default changes in C4 to C7 are SGLang-specific.
- **"21. vLLM on AWS Neuron"**: this is the answer for Trainium and Inferentia, because SGLang v0.5.22 has no Neuron backend (E1 to E5). Both engines load hardware out of tree through Python entry points (`vllm.platform_plugins` against `sglang.srt.platforms`).
