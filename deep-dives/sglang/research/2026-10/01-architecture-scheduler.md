## Mental models

1. **Three process types on a one-way ZMQ ring, and every GPU process schedules for itself.** Tokenize in the main process, schedule and run in one process per GPU, detokenize in a third; rank 0 receives and broadcasts, so every rank computes the same batch. Predicts the process count (`1 + GPUs + 1`, plus a controller under DP), why tokenizer or detokenizer CPU load never stalls the GPU loop, and why `--detokenizer-worker-num` exists. Rows A1-A5, A8, A12, F1.
2. **The scheduler runs one batch ahead.** It plans step N+1 before it knows step N's tokens; the FutureMap lets the GPU fill in the token ids. Predicts the one-step overshoot after EOS, the extra delay on back-to-back prefills, sampling waiting for grammar state, and why pipeline parallelism turns it off. Rows B4-B12, F7.
3. **Admission is a bet on early stopping.** A new request pays for its uncached prompt plus up to 4096 output tokens; running requests pay a share of their remaining output that decays from 0.7 to about 0.1. Retraction is the bet being called: the losers (fewest tokens generated) are re-queued and the share jumps back up. Predicts the retraction log, `sglang:new_token_ratio`, and what `--schedule-conservativeness` does. Rows C13-C17, E4, E7, F5, F6.
4. **Prefill first; decode runs when nothing new fits.** By default a prefill step and a decode step never share a forward, so a long chunked prompt pauses decoding for each of its chunks unless `--enable-mixed-chunk` is set. Rows C3, C18, C19, F4.
5. **Defaults are computed from your GPU.** Chunk size, decode graph size and `mem_fraction_static` all move with GPU memory and TP, and the memory fraction is derived from the other two. Rows C20, D2, D3, D6, D10.

## Where SGLang differs from vLLM (design, not benchmarks)

- Scheduling location: a scheduler in every GPU process (SGLang) vs one EngineCore per DP rank feeding worker processes (vLLM, "3. The V1 Engine Architecture"). Row F1.
- Detokenization in its own process (SGLang) vs in the API server process (vLLM, "3. The V1 Engine Architecture"). Row F2.
- Queue order: FCFS default in both; SGLang alone offers cache-aware orders (`lpm`, `dfs-weight`, `hrrn`); vLLM offers `priority` ("4. Scheduler & Continuous Batching"). Rows C4, C5, F3.
- Step composition: prefill-first alternation (SGLang default) vs one shared token budget mixing prefill chunks and decodes (vLLM, "4. Scheduler & Continuous Batching"). Row F4.
- Admission: forecast of output length with a decaying ratio (SGLang) vs prompt-fit with per-step block growth (vLLM, "4. Scheduler & Continuous Batching"). Row F5.
- KV exhaustion: both recompute; victim is fewest-generated-tokens (SGLang) vs most-recently-added (vLLM FCFS) ("4. Scheduler & Continuous Batching"). Row F6.
- CPU/GPU overlap: overlap scheduler vs async scheduling, both default on, both with one-step EOS overshoot ("4. Scheduler & Continuous Batching"). Row F7.
- Rust frontends: SGLang's replaces HTTP, tokenizer and detokenizer inside the rank-0 scheduler; vLLM's replaces the API server ("3. The V1 Engine Architecture"). Row F8.
- Memory knob: `--mem-fraction-static` (weights + KV) is a different quantity from `--gpu-memory-utilization` (the whole instance) ("27. Operations & Failure Modes"). Row F9.
- The common "SGLang LPM vs vLLM FCFS" framing compares a non-default SGLang mode against vLLM's default (C5).
