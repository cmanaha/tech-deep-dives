## Mental models


1. **The KV pool is always full of cache; free capacity means available plus evictable, and eviction pops unlocked leaves only when an allocation is short.** Predicts: a busy server shows a full pool with a low `sglang:token_usage`; `sglang:evicted_tokens_total` moves only under allocation pressure; one eviction can free more than was asked for, because a leaf goes whole. Rows: C5, C6, C14, A3, B7.
2. **A cache hit copies KV slot indices into the request's `req_to_token` row; no KV bytes move.** Predicts: hit cost does not grow with hidden size or layer count; inserting a prefix that is already cached frees the request's own copy. Rows: D1, D2, B4, B7, G5.
3. **A running request locks every node from its match up to the root, so only unlocked leaves can be evicted.** Predicts: a shared system prompt stays resident while any request using it runs; a parent becomes a candidate only after all its children are gone; evictable memory is the pool minus the union of running paths. Rows: A4, B10, C2, C6, G8.
4. **The attention backend picks the page size, and the page size is the reuse unit.** Predicts: Llama-style models reuse to the exact token on Hopper (FA3, page 1) and in 64-token steps on B200 (`trtllm_mha`, page 64); a partial last page is never cached; KV events carry one block per page. Rows: B6, B13, B14, G2, G3, F5.
5. **With HiCache on, GPU eviction demotes a backed-up node to host-only; it stays in the tree and comes back layer by layer on the next hit.** Predicts: KV events show a GPU `BlockRemoved` beside a `CPU_PINNED` store; host hits under 10 tokens are not loaded back; two instances on one L3 backend find each other's pages, because L3 keys are chained SHA-256 page hashes of tokens plus namespace. Rows: E2, E3, E8, E9, E13, F6.

Strongest for the reader: model 1. It explains the first numbers an operator sees (full pool, low usage, eviction counters) and sets up models 3 and 5.

## Where SGLang differs from vLLM


Design choices only. The 2024 speedup ratios against vLLM v0.2.5 are attributed paper and blog claims and are stale as a comparison (A7, A9).

## Section recommendation


1. **"Prefix caching with RadixAttention"**, depth tag: mechanism.
   - Opens with: the tree is an index of token runs over a pool that is always full of reusable KV. A hit copies slot indices, and eviction removes unlocked leaves only when an allocation is short.
   - Carries mental models 1 to 3 and diagrams 1 and 2. A short history block (paper, 2024 blog) sits in an `ExpandableSection` and states plainly that "RadixAttention" now names the attention layer, while the serving tree is `UnifiedRadixCache` on a Rust core (A11, A12, B2).
   - Ends on the knobs `--radix-eviction-policy` and `--schedule-policy`, and on the fact that the default policy is `fcfs`.
2. **"KV memory: pools, pages and dtype"**, depth tag: practical.
   - Opens with: how many tokens fit is free memory after weights, divided by bytes per token per layer. The attention backend quietly sets the page size.
   - Rows D1 to D11, B13, B14 and C14. Ends on `--mem-fraction-static`, `--kv-cache-dtype` and how to read `sglang:token_usage`.
3. **"HiCache: one tree across GPU, host and storage"**, depth tag: mechanism plus practical.
   - Opens with: eviction demotes a node instead of deleting it, so the tree spans tiers.
   - Diagram 3; rows E1 to E17. The DOC-CODE conflicts on prefetch timeouts and the host ratio (E6, E16) belong in the practical half. HiSparse (E20) and the session radix cache (E21) are short subsections or `ExpandableSection` blocks.
4. **KV events**, depth tag: practical. Use a short subsection, best placed next to the router or multi-node section so the producer and the consumer appear together.
   - Opens with: one block per page, published over ZeroMQ, and nothing is sent unless `"publisher": "zmq"` is set.
   - Rows F1 to F9.
