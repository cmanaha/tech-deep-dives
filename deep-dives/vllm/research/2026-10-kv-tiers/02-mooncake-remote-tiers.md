## Mental model

- Mooncake on AWS is one libfabric `efa` RDM endpoint per NIC doing one-sided `fi_write` and `fi_read` over SRD, from GPU memory (`FI_HMEM_CUDA`) or host memory (M7, M8, M9). It exists only behind the protocol string `efa` and only in the `-efa` wheels; the wheel vLLM installs is built without it (M6, M28).
- Mooncake Store is a layer on top: a master that holds metadata and leases, and clients that each lend DRAM to one pooled tier, with optional SSD offload behind each owner (M17 to M23). S3 holds master snapshots only, and no Valkey path exists (M2, M21).
- Each engine reaches Mooncake through its own protocol setting, and every default is `rdma` or `tcp`, never `efa`: vLLM `mooncake_protocol`, SGLang `MOONCAKE_PROTOCOL`, LMCache `protocol` and `MC_TE_PROTOCOL` (M26, M43, M34, M70). The NIXL MOONCAKE plugin exposes no protocol and cannot select EFA (M51).
- The other EFA path is NIXL with the LIBFABRIC backend. All four engines reach NIXL, and vLLM, SGLang and Dynamo's KVBM v1 worker default to UCX, so LIBFABRIC has to be selected (M50, M56, M57, M69, M71).
- Storage-style tiers (shared POSIX file system, S3, Valkey, SageMaker HyperPod) are reached through engine-native tiers or LMCache, not through Mooncake (matrix below).
