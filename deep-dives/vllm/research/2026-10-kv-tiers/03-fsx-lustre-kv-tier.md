## Mental model

1. Every engine at its pinned tag writes KV to FSx for Lustre as ordinary files, one file per block or chunk, named by a content hash, through the Lustre client on the EFA (LNet `efa`) or TCP network. Sharing across nodes works only when every instance computes the same hash (vLLM and llm-d set `PYTHONHASHSEED`), and Dynamo KVBM G3 does not share at all (F43, F54, F58).
2. Without GDS, the GPU-to-host hop moves the bytes: a CUDA copy into pinned host memory, then `write`/`readv` (vLLM `fs`, F41-F42), Python `tofile`/`readinto` (SGLang `file`, F61), or NIXL POSIX (`DRAM_SEG` only, F52). The Lustre client then carries the bytes over EFA, up to 700 Gbps per client (F20).
3. With GDS, cuFile and nvidia-fs move the bytes between the file and GPU memory with no host bounce buffer, up to 1,200 Gbps per client on P5, P5e, P5en, P6-B200 and P6-B300 (F18, F20, F25). At the pinned tags this path exists in LMCache's GDS backend (F46), NIXL `GDS`/`GDS_MT` with a `VRAM` buffer (F49, F51), llm-d-kv-cache's `gds_mode` (F59) and Dynamo KVBM disk-to-device onboarding (F55). vLLM's native `fs` tier, llm-d's default vLLM variant and SGLang's `file` backend have no GDS path (F41, F58, F61).
4. S3 is a separate hop, always from host memory (vLLM `obj`, LMCache `s3`, KVBM G4, NIXL `OBJ`; F44, F50, F53, F56). An FSx data repository association can export files to S3 Standard underneath the engine (F39, F65), but no engine at these tags reads that export back as a KV tier.
5. No engine or connector at these tags evicts from a shared file system tier; capacity is the operator's job: llm-d's PVC evictor, SGLang's per-process LRU, or FSx release tasks counted in days (F39, F43, F58, F60, F61).

## Sizing arithmetic

Every number here is derived. Inputs are named; decimal GB and MB are assumed for vendor "MBps" unless stated.

1. Unit conversions [derived]: 1,200 Gbps = 150 GB/s; 700 Gbps = 87.5 GB/s; 100 Gbps = 12.5 GB/s (inputs F20).
2. F24 refinement, capacity to feed one GDS client at the ceiling [derived]: disk-bound (writes, uncached reads) 150,000 MBps / 1,000 MBps per TiB = 150 TiB, rounded up to the EFA PERSISTENT-1000 step of 4.8 TiB = 32 x 4.8 = 153.6 TiB. Cache-resident reads are network-bound: 150,000 / 2,600 = 57.7 TiB, so 13 x 4.8 = 62.4 TiB. For the 700 Gbps non-GDS path (vLLM `fs`, SGLang `file`): 87,500 / 1,000 = 87.5 TiB, so 19 x 4.8 = 91.2 TiB (inputs F20, F21, F29). This assumes per-TiB rates add linearly and that one client reaches the documented ceiling; neither is shown by an AWS measurement.
3. Object storage servers [derived]: EFA PERSISTENT-1000 stores 4.8 TiB per OSS, so 4,800 MBps of disk throughput per OSS; 150 GB/s needs at least 32 OSS (31.25). Over ENA, 100 Gbps from one client at 5 Gbps per client-OSS pair needs at least 20 OSS, that is 48 TiB at 2.4 TiB per non-EFA OSS (inputs F20, F29).
4. EFA connection budget [derived]: 1,024 connections / 8 default interfaces = 128 P5, P5e, P5en or P6-B200 clients per file system; / 16 = 64 p6-b300.48xlarge clients (inputs F27). More clients need fewer interfaces each, which lowers per-client throughput ("Instances with more EFA interfaces typically support higher throughput").
5. KV bytes per token [derived, inputs as stated by the AWS Storage Blog, F5]: Llama 3.1 405B, BF16: 2 x 126 x 8 x 128 x 2 B = 516,096 B per token.
6. vLLM `fs` file size [derived, inputs F79, F40, F58, item 5; assumes BF16 KV, one KV cache group, no MLA]: one file holds one chunk for all ranks, so 405B at `block_size` 256 (llm-d config) is 256 x 516,096 = 132,120,576 B (126 MiB) per file, and at `block_size` 16 (vLLM doc example) 8,257,536 B (7.9 MiB) per file.
7. Striping of those files under the default layout [derived, inputs F35, item 6]: a 7.9 MiB file sits on one OST (first component, up to 100 MiB, stripe count 1); a 126 MiB file puts its first 100 MiB on one OST and the rest in the 8-stripe component.
8. Metadata load from file-per-chunk writes [derived, inputs F34, F41, item 6]: writing at 150 GB/s with 7.9 MiB files is 150e9 / 8,257,536 = 18,165 files/s; at 2 create/open/close operations per provisioned metadata IOPS that needs about 9,083 IOPS, so the 12,000 level, before counting the rename each store performs (rename cost for files is not in the AWS table; see Open items). With 126 MiB files it is 1,135 files/s, about 568 IOPS.
9. Time to pull one prefix [derived, inputs item 1, item 5]: 100,000 tokens of 405B KV is 51.6 GB, which takes 0.34 s at 150 GB/s, 0.59 s at 87.5 GB/s and 4.1 s at 12.5 GB/s. At the blog's 50,000-token threshold (F11): 25.8 GB, 0.17 s at 150 GB/s. These are ceilings; the only AWS GDS measurement on FSx located (weights, F67) ran at 64 to 78 GB/s.
10. ML blog consistency check [derived, inputs F66, F21]: 96 TiB x 1,000 MBps/TiB = 96,000 MBps, which is 89.4 GiB/s if MB is decimal and 93.75 GiB/s if MB is MiB. The blog's "approximately 94 GiB/s" matches the binary reading (see Open items).
11. Share of the fabric [derived, inputs F20, F66]: the 1,200 Gbps FSx client ceiling is 37.5% of a p5en's 3,200 Gbps EFA aggregate, and with the default 8 of 16 interfaces given to FSx, the remaining 8 carry inter-node traffic. The AWS Storage Blog says to account for both (F12).
