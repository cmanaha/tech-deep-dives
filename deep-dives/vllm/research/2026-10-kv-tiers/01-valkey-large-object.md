## Mental model

- Two paths. RESP over an ordinary TCP connection carries the command, the key and the client's `(rkey, addr, len)` memory descriptors. The object bytes move separately, one-sided, over EFA (rows V5-V8).
- The server's NIC moves the bytes. `BLOB.RDMA_GET` is a server-posted `fi_writemsg` into client memory and `BLOB.RDMA_SET` is a server-posted `fi_read` from it. The client CPU only registers memory and waits for the reply, which comes after delivery completes (V7, V9).
- Server memory is a host DRAM pool registered with EFA once at startup and on growth. Client memory is whatever the client registered. The located clients (glide-rdma and LMCache PR 5556) register pinned host memory, LMCache's L1 arena, so today the module is a remote host-memory tier sitting below LMCache L1. It does not write into GPU memory (V15, V16, V43, V49).
- The tier is a non-durable, non-replicated cache node: DRAM by default, with optional local NVMe in Tiered mode (one O_DIRECT file per object, DRAM as read cache, always staged through host DRAM). Everything is lost on restart, and replicas get nothing (V20-V25).

## Maturity and status

As of 2026-10-24:
- Module: crate 0.1.0, no tags or releases, 101 commits since 2026-08-07. HEAD 7510b948 (2026-10-22). Command names were split into `BLOB.TCP_*` / `BLOB.RDMA_*` in October 2026 (V1, V4, V38).
- Governance: the Valkey core team accepted it as a valkey-io repository on 2026-09-21, with an API that stays "experimental/beta" until a 1.0 release. The proposer names AWS as sponsor and maintainer. Issue 4743 is open with label `major-decision-approved` (V35-V37).
- Gaps in code at this SHA: no persistence, no replication, object ids not unique across cluster nodes, no request coalescing on cold Tiered GETs (V24, V25, V33).
- Testing: CI runs only the libfabric `tcp` provider on GitHub-hosted arm runners against Valkey `unstable`. EFA hardware is exercised only in a benchmark workflow on a self-hosted i8ge runner, which runs TCP_GET benchmarks (V28, V29).
- Client side: nothing has been released. The `glide-rdma` crate merged on 2026-10-21. The glide-core integration (PR 7412) and the LMCache adapter (PR 5556) are open. The Python glide-sync RDMA API LMCache needs is in no release (latest stable 2.5.3). The LMCache PR body points to a fork branch for it (V41-V48).
- AWS managed services: nothing located. No ElastiCache or MemoryDB documentation or What's New entry covers this module, RDMA, EFA or customer-loaded modules (V58, V59). It runs only as self-managed Valkey on EC2.
- Inference engines: no direct integration in vLLM v0.32.0, SGLang v0.5.22 or Dynamo v1.6.0. vLLM would reach the module through LMCache's multiprocess connector once PR 5556 and a glide release land (V62).

## Latency and bandwidth

Only numbers located during this research appear here. None is an AWS statement. None includes an inference engine in the loop.
- **LMCache adapter, RDMA versus TCP** [Tier 2: PR author claim, LMCache PR 5556 comment 6304983743, 2026-10-21]. Setup: two c8gn.16xlarge (200 Gbit/s EFA, 1 network card, per [Tier 1: AWS docs]) in one placement group, `lmcache bench l2` at adapter level, 32 keys per submit, server `fabric-provider EfaDirect`. Results: 16 MiB loads at 197.8 to 198.6 Gbit/s over RDMA with 4 to 16 workers, against 32.8 to 62.5 Gbit/s over TCP; 256 KiB loads at 63.3 versus 40.5 Gbit/s (16 workers). Per-submit load p50 is 33.5 ms for 32 x 16 MiB with 1 worker and 4.5 ms for 32 x 256 KiB with 1 worker. The bytes land in host L1 memory (V65).
- **valkey-benchmark EFA mode** [Tier 2: PR author claim, valkey-io/valkey PR 4858 commit 42349be5, 2026-10-09]. About 190 Gbit/s of 16 MiB GETs on "aws c8gn.16xl": 1,496.08 requests per second, latency avg 5.343 ms, p50 5.367 ms, p99 6.135 ms, 8 clients, 8 threads. Client and server placement not stated (V63).
- **In-repo design doc** [Tier 2: project claim, docs/STORAGE_DESIGN.md at 7510b948]. On i8ge: `fi_mr_reg` costs ~333 microseconds per call, and per-request registration drops 4 KB throughput from 138K to 3K requests/s. One NVMe cache miss is "~15μs on i8ge" (docs/STORAGE_DESIGN.md#L337). "Current scale" of EFA streaming is quoted as 100K rps at 4 KB and 50K rps at 1 MB, with no setup (V30).
- **TCP baseline for context** [Tier 2: valkey.io blog, 2026-10-20]: a three-shard Valkey cluster sustained about 7.4 GB/s of LMCache reads against a ceiling near 11.25 GB/s (about 30 Gbps per 16xlarge shard) (V61).
- No AWS-published latency or bandwidth figure for this module, or for Valkey over EFA, was located during this research.
