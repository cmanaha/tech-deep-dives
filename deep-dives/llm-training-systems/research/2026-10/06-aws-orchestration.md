### D. SageMaker HyperPod: orchestrators, resiliency and restart

**T06-1. **T06-7. Slurm auto-resume is per job step: launch with `srun --auto-resume=1` inside an exclusive allocation, put all setup in one srun entrypoint, and derive the node list from `scontrol` rather than `$SLURM_JOB_NODELIST`, which can be stale after a resume. With auto-resume on, faulty nodes are always replaced, never rebooted, and the step restarts from the last checkpoint the job saved. Jobs on GRES nodes are requeued and restart from the beginning.**
- Location: SageMaker AI Developer Guide, "Automatic node recovery and auto-resume" (Slurm), sections "Running a training job with ... auto-resume", "How automatic node recovery and auto-resume work together"; "Orchestrating SageMaker HyperPod clusters with Slurm", "Resiliency against hardware failures".

**T06-12. ### 3.3 Decision notes [our reading throughout; each note cites the entries it rests on]

1. **Many short or medium fine-tuning jobs, no standing cluster wanted: SageMaker training jobs.** Billing stops with the job (T06-23); warm pools cover an edit-run loop (T06-26); managed Spot with checkpoints absorbs lost first-hour intervals (T06-27); Batch service jobs add team queues (T06-51). Use SDK v3 `ModelTrainer` and bring the framework in the container; SMP v2 is frozen at PyTorch 2.5.1 (T06-24, T06-28).
2. **Long pre-training or continuous multi-team use of a fixed GPU pool, Slurm-native team: HyperPod Slurm.** AWS owns node health, burn-in and replacement; the job owns checkpoints and a single-srun entrypoint (T06-4 to T06-7). The bill runs while idle (T06-18).
3. **Same, Kubernetes-native team: HyperPod EKS.** Adds task governance, process-level restarts, elastic and checkpointless training (T06-12 to T06-16), at the price of version constraints that lag upstream (T06-9, C06-2).
4. **Kubernetes team that wants its own control: self-managed EKS.** Node repair now exists in EKS itself (T06-43); the team adds Kueue for gang admission and topology (T06-44, T06-47) and picks a job API mid-migration (T06-46). Use node groups or Karpenter for a fixed fleet; Auto Mode's per-node fee is large at P5 scale (T06-41, section 3.2).
5. **Slurm team that wants AWS to run the controller but keep its own images: PCS.** Health checks and requeue remain the team's (T06-37); budget the controller and the $0.64 per P or Trn instance-hour (T06-36); plan a yearly Slurm major upgrade (T06-32).
6. **ParallelCluster:** keep running if already in place (supported to 2028-02-20), but start new clusters on PCS or HyperPod Slurm, as AWS's own banner advises (T06-38).
7. **Trainium:** every path gives devices and capacity; none of the managed paths documented here ships a current Trainium training recipe (T06-52, T06-53). Pick the path by who will build the Neuron software stack, and link the silicon dive for TorchNeuron and TorchTitan Neuron.
8. **Whatever the path, the training script owns three things:** writing and reloading checkpoints (T06-7, T06-27), checkpointing before a Capacity Block or training plan window closes, 30 minutes before its end (T06-30, T06-34, T06-42), and logging progress per step so watchdogs can see hangs (T06-12).

## 4. Mental models worth teaching

1. **Node recovery is not job recovery.** Health agents find and replace bad nodes (HyperPod HMA, EKS node repair); getting the job running again needs a job-level mechanism plus a checkpoint the job wrote itself (T06-4, T06-6, T06-7, T06-43).
2. **A cluster per job or a cluster per team.** Training jobs bill for the job and pay a provisioning wait each time; HyperPod and PCS bill for the cluster's life and start jobs immediately (T06-18, T06-23, T06-26, T06-36).
3. **Synchronous training needs all-or-nothing admission.** One missing rank stalls every other rank at the first collective, so Kubernetes needs a gang scheduler that Slurm has built in (T06-44, T06-47, T06-50).
4. **Elasticity lives in the data-parallel dimension.** Tensor and pipeline layouts are baked into each rank's shard; adding or removing whole data-parallel replicas, with the global batch held fixed, changes speed but not the optimisation (T06-13).
5. **A hang watchdog needs a heartbeat.** HyperPod's hang detection matches log lines; a step that prints nothing cannot be watched (T06-12).
6. **The reservation window is a hard deadline.** EC2 begins terminating Capacity Block instances 30 minutes before the end, and every orchestrator inherits that (T06-30, T06-34, T06-42).
7. **For Trainium, the path decides who builds the software.** Devices and capacity exist on every path; the training stack does not come with any of them at the versions read (T06-52, T06-53).

## 5. Contradictions

**C06-1. UltraServer instance count: 18 or 17.** The HyperPod overview says an NVL72 UltraServer combines 18 instances and fills 18 before spilling (https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html); the HyperPod Slurm page says 17 then 3 for a 20-instance request (https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-slurm.html). Both Tier 1, accessed 2026-10-30 (T06-10). Area 05 settles the instance count from the EC2 documentation; the placement rule (fill one UltraServer first) is consistent on both pages.

**C06-2. HyperPod training operator support matrix versus the platform around it.** The operator page lists Kubernetes 1.28 to 1.33, Kueue v0.12.2 and v0.12.3, PyTorch 2.4.0 to 2.7.1 (T06-9). The HyperPod EKS AMI for Kubernetes 1.34 shipped 2026-01-25 (T06-11); EKS standard support now covers 1.34 to 1.37 and 1.33 is on extended support (T06-40); Kueue is at v0.20.4 (T06-47); the checkpointless container runs PyTorch 2.6.0 inside the range (T06-14). No code was read to say which side is current; treat the doc table as possibly stale and verify on a test cluster before relying on it.

**C06-3. HyperPod recipes framework statement versus Neuron status.** The recipes page says the training adapter is built on NeMo "and the Neuronx Distributed Training package" (T06-19). NxD Training is end-of-support on current Neuron releases (RL F06-45 and U18 in `deep-dives/rl-agentic-loops/research/2026-10/06-aws-paths.md`), and the recipes repository has had no Trainium recipe since v2.0.0 (T06-20). Code is the authority: at 2.0.11 the recipes are GPU only.

**C06-4. Trainium Slurm tutorial versus recipes code.** The tutorial launches `launcher_scripts/llama/run_hf_llama3_8b_seq8k_trn1x4_pretrain.sh` with `recipes=training/llama/hf_llama3_8b_seq8k_trn1x4_pretrain` after cloning the repository's default branch (T06-52). Neither path exists at 2.0.11 or at v2.0.0; both existed at v1.5.1 (T06-20). Verdict: the tutorial is STALE from v2.0.0 (2025-12-03).

**C06-5. HyperPod CLI documentation versus CLI code.** The Developer Guide page documents `hyperpod start-job` and requires the Kubeflow Training Operator; the CLI README at v3.13.0 documents `hyp create hyp-pytorch-job` against the HyperPod training operator (T06-22). The README is the nearer source to the code; the doc page likely describes the pre-v3 CLI [our reading].

**C06-6. SMDDP version.** The SMDDP release-notes page ends at v2.5.0 (2024-10-17); the SMP v2.8.0 release notes (2025-04-01) list "SMDDP library v2.6.0" in the SMP container (T06-25). Two Tier 1 pages; the SMDDP page omits a release the SMP page ships. Practical effect is nil on P5 and later (SMDDP is P4-only, EFA dive).

**C06-7. Kubernetes job API drift.** Kueue v0.20.4 deprecates its Kubeflow v1 integrations (PyTorchJob) in favour of TrainJob or JobSet; Kubeflow calls TrainJob alpha; HyperPod EKS documents auto-resume for PyTorchJob and its CLI page still requires the Kubeflow Training Operator (T06-22, T06-46). Version drift, not an error on any single page.

**C06-8. Auto-resume node-count condition.** The HyperPod Slurm overview limits resume-after-replacement to "clusters with more than 16 nodes" (T06-7); the auto-resume page itself states no node-count condition. Unresolved (U06-1).
