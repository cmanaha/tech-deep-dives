### G3. How did DeepSeek-V3 split 61 layers over 16 stages?

The paper does not publish per-stage counts. What it states: "DeepSeek-V3 applies 16-way Pipeline Parallelism (PP)"; "We set the number of Transformer layers to 61"; "The multi-token prediction depth 𝐷 is set to 1"; and, for DualPipe, "we deploy the shallowest layers (including the embedding layer) and deepest layers (including the output head) of the model on the same PP rank" (https://arxiv.org/pdf/2412.19437v2, Sec 3.2.1 and 4.2). So the first and last pipeline positions share one rank, and the per-stage count is not given.

Two reference points, neither of them DeepSeek's statement:
- Megatron Core's `pipeline_model_parallel_layout` docstring gives the example `'Et*3|(tt|)*29,m|L'`, where 'E' is embedding, 't' a decoder layer, 'm' the MTP layer and 'L' the loss (core_v0.20.0 `transformer_config.py` lines 125 to 150). Expanded, that is 32 stages holding 3 + 29 x 2 = 61 decoder layers plus one MTP stage and one loss stage, which fits PP 16 with two virtual stages per rank [derived]. The shape matches DeepSeek-V3, but the docstring does not name the model [SPECULATIVE that it was written for it].
- TorchTitan v0.4.0's default would place 61 layers on 16 stages as 3 + 14 x 4 + 2 (63 effective units, the first 15 stages get 4 and the last gets 3) [derived].

Text the page can carry: "DeepSeek-V3 ran 61 layers on PP 16 under DualPipe, which places the shallowest and deepest layers on the same rank; the paper does not give the per-stage count (T02-40, T02-71)."

### G4. FSDP hybrid-sharding cross-host formula (U02-13)

Source: LaTeX of 2304.11277v2 (https://arxiv.org/e-print/2304.11277v2, `text/design_sharding.tex` lines 4, 54, 73). Quoted in W2-14. The printed formula is 2M(W-1)/(GW); the definition on line 54 makes the host-local sharding factor F = G, not the printed F = W/G (C02-1 holds in the source).

Exact ring cost, re-derived: with G GPUs per host and W in total, each GPU owns an M/G gradient shard and all-reduces it with the W/G GPUs of the same local rank on other hosts, so it sends 2 x (M/G) x (W/G - 1)/(W/G) = 2M(W-G)/(GW) bytes across hosts [derived]. For section 8's 8B example (M = 16.06 GB, G = 8, W = 32): 2 x 16.06 x 24 / 256 = 3.01 GB per step, against 3.89 GB from the paper's printed form. ## Orchestrator addendum (2026-10-31, build): cross-instance collectives are priced per instance

Raised by the section 7 author during the build and checked by the orchestrator against AWS's own sample output. It changes the verdicts of W2-9, W2-15 and W2-51 from HOLDS to WRONG on the bandwidth model (their arithmetic reproduces; the divisor does not).

**Evidence.** https://raw.githubusercontent.com/aws-samples/awsome-distributed-training/3a1002576ccef26e66ba714303b10ccdaa645691/micro-benchmarks/nccl-tests/README.md (accessed 2026-10-31), the table under "All_reduce ... 8B to 16GB on 2x p5.48xlarge": the 17179869184-byte row reads `66132  259.78  487.09` (time in us, algbw and busbw in GB/s). A per-GPU count over 50 GB/s of EFA per GPU predicts at least 2 x 15/16 x 17.18 GB / 50 GB/s = 0.64 s for that row; the run took 66 ms.

**Model.** NCCL builds several rings or trees per collective and spreads the hops that cross the instance boundary over all of the instance's network cards, so the binding resource for a collective whose group has several members per instance is the instance's EFA bandwidth (3,200 Gb/s = 400 GB/s on p5.48xlarge and p5en.48xlarge, T05-3), not one GPU's share. Lower bound per instance for a group spanning M instances: (M-1)/M x S for an all-gather or reduce-scatter of S bytes, 2(M-1)/M x S for an all-reduce; a flat ring moves (n-1)/n x S per instance for a group of n ranks. For the AWS row: at least 2 x 1/2 x 17.18 = 17.2 GB per instance, 43 ms at 400 GB/s, which the measured 66 ms respects; the flat-ring count, 32.2 GB and 80 ms, is above it, so NCCL did better than a flat ring there [derived, our reading of the sample]. Where a group has one member per instance (DP in TP 8 x PP 4 x DP 8, FSDP in TP 8 x FSDP 32, HSDP's replica all-reduce), eight such groups share the instance and the per-instance count equals the per-GPU count over 50 GB/s, so W2-42 and W2-44 stand unchanged.
