## 2. Claim register

### A. PyTorch distributed at v2.15.0: the primitives everything else reuses

**T03-1. FSDP2 (`fully_shard`) shards each parameter on dim 0 as a DTensor, all-gathers a group's parameters before its forward, frees them after forward and re-all-gathers them in backward when `reshard_after_forward` is true, then frees them again and reduce-scatters the gradients. The default (`None`) is true for every non-root module and false for the root; an integer reshards to a smaller world size (for example the GPUs of one node) so the backward all-gather stays local.**
- Location: pytorch v2.15.0, `torch/distributed/fsdp/_fully_shard/_fully_shard.py` lines 100 to 222 (signature and docstring), 258 to 272 (default resolution).
- Verdict: NEW
- Evidence: https://github.com/pytorch/pytorch/blob/31a77fc9c0a7c6fff15a1ff58c743f53b1a9d457/torch/distributed/fsdp/_fully_shard/_fully_shard.py#L100-L222 | Tier 1, code (docstring and code at the tag) | code behaviour, default value | "Before forward, FSDP all-gathers the sharded parameters across the data-parallel workers to get the unsharded parameters for forward computation. If ``reshard_after_forward`` is ``True``, then FSDP frees the unsharded parameters after forward and re-all-gathers them in backward before gradient computation. After gradient computation, FSDP frees the unsharded parameters and reduce-scatters the unsharded gradients across data-parallel workers." "If ``None``, it is set to ``True`` for non-root modules and ``False`` for root modules." "If an ``int``, then this represents the world size to reshard to after forward. It should be a non-trivial divisor of the ``mesh`` shard dim size ... A choice may be the intra-node size (e.g. ``torch.cuda.device_count()``)." On a 2D mesh: "parameters are sharded across the 1st dim and replicated across the 0th dim (HSDP)". (accessed 2026-10-30)
- Use in dive: the code-level statement of ZeRO-3 as PyTorch ships it: two all-gathers and one reduce-scatter per FSDP unit per forward-backward, which is T02-7's 3Psi. The integer option is ZeRO++'s hpZ idea (T02-11) inside PyTorch. Builds a mental model and is practical.
- Link: `02-parallelism.md` T02-7 to T02-9 (the maths).

**T03-2. Under gradient accumulation FSDP2 communicates on every micro-batch by default: each parameter group starts with `reduce_grads = True` and `reshard_after_backward = True`, so every backward reduce-scatters and every next forward all-gathers again. `set_requires_gradient_sync(False)` is the FSDP2 equivalent of FSDP1's `no_sync`: gradients then accumulate unsharded, in `reduce_dtype` if set. `set_reshard_after_backward(False)` keeps parameters unsharded between micro-batches, trading memory for the skipped all-gather. For HSDP, `set_requires_all_reduce(False)` keeps the in-group reduce-scatter and skips only the cross-replica all-reduce.**
- Location: pytorch v2.15.0, `torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py` lines 269 to 276 (defaults) and 712 to 726 (post-backward branch); `_fully_shard.py` lines 597 to 648 (`set_requires_gradient_sync`, `set_requires_all_reduce`) and 687 to 700 (`set_reshard_after_backward`).
- Verdict: NEW (closes U02-11 for the code question; the byte counts stay with area 02)
- Evidence: https://github.com/pytorch/pytorch/blob/31a77fc9c0a7c6fff15a1ff58c743f53b1a9d457/torch/distributed/fsdp/_fully_shard/_fully_shard.py#L597-L700 | Tier 1, code | code behaviour, default value | "Sets if the module should sync gradients. This can be used to implement gradient accumulation *without communication*. For HSDP, this controls both reduce-scatter and all-reduce together. This is the equivalence of `no_sync` in FSDP1." "Unsynchronized gradients accumulate on unsharded parameters in ``MixedPrecisionPolicy.reduce_dtype`` if set". "Before gradient clipping or an optimizer step, enable the required reductions and call ``set_is_last_backward(True)`` for the final backward." `set_requires_all_reduce`: "This can be used to implement gradient accumulation with only reduce-scatter but not all-reduce for HSDP." `set_reshard_after_backward`: "This can be used during gradient accumulation to trade off higher memory for reduced communication since the unsharded parameters do not need to be re-all-gathered before the next forward." https://github.com/pytorch/pytorch/blob/31a77fc9c0a7c6fff15a1ff58c743f53b1a9d457/torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py#L269-L276 | Tier 1, code | default value | `self.reduce_grads: bool = True`, `self.all_reduce_grads: bool = True`, `self.reshard_after_backward: bool = True` (accessed 2026-10-30)
- Use in dive: practical, and it decides the communication check of the "set my ranks" procedure. Per step with k micro-batches, in units of Psi before the (n-1)/n ring factor [derived from T03-1, this entry and T02-7]: default, 2k all-gathers and k reduce-scatters (3k Psi); with gradient sync off on all but the last micro-batch, k reduce-scatters become 1, and with `reshard_after_backward` also off on non-final micro-batches each later forward skips its all-gather (about k + 1 all-gathers in total) [our reading of the code path, not measured; a Tier 0 trace on one node would confirm]. The memory price is a full unsharded gradient (and, without resharding, full parameters) per rank for the whole accumulation window.
- Link: `02-parallelism.md` U02-11 and section 3.3 (47 GB versus 373 GB per GPU per step).

## 4. Mental models worth teaching

1. **Engines and front ends.** A handful of engines implement parallelism (PyTorch FSDP2 and DTensor, Megatron Core, DeepSpeed); everything else is a front end that picks a config and a loop (TorchTitan, Megatron Bridge, AutoModel, Accelerate, the Trainer, and all post-training frameworks). Choosing a framework is mostly choosing an engine. (T03-16, T03-23, T03-26, T03-42, T03-50)
2. **One idea, four names.** ZeRO stages 1 to 3 are DeepSpeed's `stage`, Megatron-FSDP's `optim`, `optim_grads`, `optim_grads_params`, Megatron's distributed optimizer (stage 1), and PyTorch's `fully_shard` (stage 3; with `reshard_after_forward=False` it keeps parameters unsharded from forward to backward, close to stage 2 [our reading]). (T03-1, T03-17, T03-18, T03-29; T02-8)
3. **Defaults talk on every micro-batch.** Gradient accumulation does not reduce FSDP traffic unless the trainer turns sync off between micro-batches; PyTorch and TorchTitan leave it on by default. (T03-2, T03-3, W1)
4. **"Reshardable" means three different things.** DCP reshards at load; Megatron reshards weights at load but its default optimizer state only across DP; DeepSpeed reshards through an offline conversion. Plan a node-count change before the checkpoint is written. (T03-9, T03-22, T03-32)
5. **Precision support is gated by silicon and by framework version.** H100 FP8 lives in Transformer Engine recipes (Megatron, Accelerate, AutoModel); TorchTitan dropped it in v0.4.0. MXFP8 needs Blackwell or Trainium3. Trn2 trains in BF16. (T03-13, T03-19, T03-36, T03-53)
6. **On Trainium a rank is a logical NeuronCore,** so a trn2.48xlarge is 64 ranks and TP 4 spans one chip; the rank arithmetic of area 02 carries over with that substitution. (T03-38, W3)
7. **Maturity labels are part of the spec.** The PyTorch-native stack is built on APIs labelled alpha, experimental and prototype; TorchNeuron and TorchTitan Neuron are beta; NxD Training is end-of-support; torchtune is unmaintained; NeMo's repository is now speech. Pin versions and read the label before the feature list. (T03-6, T03-25, T03-34, T03-36, T03-48)

## 5. Contradictions

**C03-1. TorchTitan's Llama 3 README versus its v0.4.0 code.** `torchtitan/models/llama3/README.md` lines 69 to 70 list "torch.compile, Float8, async TP, Interleaved 1F1B" in the convergence test table; v0.4.0 removed legacy Float8 training (release notes) and has no Float8 module (T03-13). The README describes v0.3.0 behaviour; code and release notes are the authority.

**C03-2. Megatron-LM README badge versus tag.** At `core_v0.20.0` the README badge reads "release-0.19.0" (T03-16). Cosmetic; cite the tag, not the badge.

**C03-3. Megatron's distributed-checkpointing workflow versus its code.** `docs/api-guide/core/dist_checkpointing.md` says `dp_reshardable` is "Not reshardable - not possible to change model parallelism", then its workflow says "Change model parallelism for train config. - Resume training with `--dist-ckpt-optim-fully-reshardable`", which reads as if a `dp_reshardable` checkpoint loads under new TP or PP once the flag is on. The code records the sharding type at save time and documents `dp_reshardable` as resharding "only in DP dimension" (T03-22). Code is the authority: save with the flag before changing TP or PP. Whether the load path can convert an old `dp_reshardable` checkpoint is U03-3.

**C03-4. Four end dates for NxD Training in AWS's own announcements** (2025-12-16: from PyTorch 2.10; 2026-02-26: last in 2.28; 2026-05-20: maintenance mode from 2.30; 2026-06-28: off the DLAMIs from 2.31; archive: end-of-support as of 2.32), all still published in the v2.33.0 docs (T03-35). The latest statement governs: last release 2.31.0, end-of-support from 2.32 (T03-34, RL F06-45).

**C03-5. Accelerate's `ParallelismConfig` docstring versus its code.** The docstring says `cp_size` is "Currently not supported, but reserved for future use and enabled for downstream libraries."; `Accelerator` runs `context_parallel` when `cp_size > 1` under FSDP2 ("`context_parallel` is currently supported with FSDP2 and requires `parallelism_config.cp_size` > 1.") (T03-39). Code is the authority.

**C03-6. One FSDP plugin, two defaults.** Accelerate v1.15.0 defaults `fsdp_version` to 1; transformers v5.22.1 passes version 2 unless told otherwise (T03-40). Not a bug in either, but the same model and config change FSDP generation with the entry point.

**C03-7. HyperPod recipes doc versus both frameworks it names.** The SageMaker page says the recipes' adapter "is built on the NVIDIA NeMo framework and the Neuronx Distributed Training package" (T06-19). At current tags NVIDIA/NeMo is a speech repository (T03-25) and NxD Training is end-of-support (T03-34). Extends C06-3: the statement holds only for NeMo 2.x and Neuron releases up to 2.31.

**C03-8. TorchTitan paper venue.** `02-parallelism.md` lists 2410.06511v3 as a preprint (arXiv metadata carries no venue); the ICLR 2025 virtual poster page lists "TorchTitan: One-stop PyTorch native solution for production ready LLM pretraining" (https://iclr.cc/virtual/2025/poster/29620, accessed 2026-10-30). Peer-reviewed, ICLR 2025, confirmed from the venue's page.

**C03-9. FSDP2 gradient-reduction dtype, version drift.** PyTorch 2.15 changed the default reduction dtype under `reduce_dtype=None` from `param_dtype` to the parameter's gradient dtype; FSDP1 still reduces in `param_dtype` (T03-4). Any byte count or convergence note about FSDP2 mixed precision must name the PyTorch version.

**C03-10. MXFP8 on Neuron: release notes versus fork code.** TorchNeuron's 2.33.0 release notes say the release "does not include TorchAO integration or composite MXFP8 data type support" (T03-36); the TorchTitan Neuron fork at `release-2.33.0` ships an MXFP8 path on "torchao with Neuron MXFP8 support", gated on Trn3 (T03-53). Both agree that Trn2 has no MXFP8 training; whether the Trn3 MXFP8 path works on the public 2.33.0 packages is U03-4.

## 7. Reading path for a newcomer

1. PyTorch `fully_shard` docstring at v2.15.0 (T03-1, T03-2): the shortest precise description of what sharded data parallelism does per forward and backward, and the knobs that change it.
2. Megatron's distributed optimizer page (T03-17): one table that turns the 16-bytes-per-parameter idea into the numbers a real framework uses.
3. TorchTitan's configuration guide and `ParallelismConfig` (T03-11, T03-12): how the parallel degrees compose into one mesh, in code a reader can follow end to end.
4. Megatron Bridge's Llama 3 recipes (T03-24) next to Megatron's parallelism guide (T02-52): what NVIDIA actually ships as starting layouts.
5. Megatron's low-precision page (T03-19) and TorchTitan's MXFP8 README (T03-13): which FP8 recipe exists on which GPU.
6. DCP's page, Megatron's distributed-checkpointing page and DeepSpeed's Universal Checkpointing tutorial (T03-9, T03-22, T03-32), read together: three answers to "can I restart on a different cluster shape?"
7. The Neuron 2.33.0 TorchTitan Neuron overview (T03-37, T03-38), after the GPU material, so the substitutions (logical cores as ranks, BF16 only on Trn2) stand out.
8. The LoRA paper's practical-benefits paragraph (T03-43) and LLaMA-Factory's hardware table (T03-45): the memory arithmetic for fine-tuning in two short reads.
