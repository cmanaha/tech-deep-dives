### A. AWS Batch (section 24)

AWS Batch is a managed job queue: the user submits a container job to a queue, and Batch starts EC2 instances for it, runs it, retries it and removes the instances when the queue is empty. The entries below are the properties that decide whether a workload of the loop fits it.

**F09-1. AWS Batch on Fargate does not run GPU jobs. The Batch user guide recommends EC2 over Fargate when a job needs a GPU, more than 32 vCPUs, more than 244 GiB of memory or a custom machine image. The same page gives the start-up difference: about 30 seconds on Fargate against a few minutes for a new EC2 instance.**
- Location: AWS Batch User Guide, "When to use Fargate"
- Verdict: CARRIED (seed 03, re-fetched)
- Evidence: https://docs.aws.amazon.com/batch/latest/userguide/when-to-use-fargate.html | Tier 1, first-party docs | documentation of a limit | "Typically, it takes a few minutes to spin up a new Amazon EC2 instance. However, jobs that run on Fargate can be provisioned in about 30 seconds." and "we recommend that you use Amazon EC2 if your jobs require any of the following: More than 32 vCPUs More than 244 gibibytes (GiB) of memory A GPU A custom Amazon Machine Image (AMI)" (accessed 2026-11-20)
- Use in dive: section 24, the first fork: every GPU workload of the loop is an EC2-backed compute environment. The "few minutes" is the documented cold-start floor for a queue scaled to zero (F09-13).

**F09-2. Since 25 August 2026 Batch has a third compute environment type, Amazon ECS Managed Instances: AWS manages the machine image, patching and instance lifecycle, and GPU instances are supported, on On-Demand, Spot or reserved capacity. The docs send four needs back to EC2 managed compute environments: multi-node parallel jobs, custom AMIs or launch templates, control over allocation strategies, and a warm pool (`minvCpus`).**
- Location: What's New post "AWS Batch now supports Amazon ECS Managed Instances" (Posted on: Aug 25, 2026); AWS Batch User Guide, "When to use Amazon ECS Managed Instances"; document history row dated August 24, 2026
- Verdict: CARRIED (seed 03, re-fetched; the seed gave "Aug 2026", the post is dated Aug 25, 2026)
- Evidence: https://aws.amazon.com/about-aws/whats-new/2026/08/aws-batch-on-ecs-managed-instances/ | Tier 2, launch announcement | "AWS Batch now supports Amazon ECS Managed Instances (ECS MI) as a new compute option, enabling you to run GPU-accelerated and compute-intensive batch workloads on AWS-managed infrastructure." and "submit jobs using On-Demand, Spot, or reserved capacity" ; https://docs.aws.amazon.com/batch/latest/userguide/when-to-use-ecs-managed-instances.html | Tier 1, first-party docs | documentation of a limit | "Use Amazon EC2 managed compute environments if: You need multi-node parallel (MNP) jobs. You require custom AMIs or launch templates. You need fine-grained control over allocation strategies. You need a minimum capacity warm pool (minvCpus)." (accessed 2026-11-20)
- Use in dive: section 24, the 2026 news for Batch. `[our reading]`: a single-GPU job on a stock image (an ACT fine-tune, a state-only simulation run) fits it; a job that needs a custom Isaac Sim image baked into an AMI, or a Capacity Block through a launch template (F09-17), does not.

**F09-3. Batch has six instance allocation strategies for EC2 and Spot compute environments. `BEST_FIT` (the default) picks the lowest-cost fitting type and waits for it. `BEST_FIT_PROGRESSIVE` adds other types when the first is unavailable. `BEST_FIT_PROGRESSIVE_ORDERED` follows the order of the `instanceTypes` list and is On-Demand only. `SPOT_CAPACITY_OPTIMIZED`, `SPOT_PRICE_CAPACITY_OPTIMIZED` and `SPOT_CAPACITY_OPTIMIZED_PRIORITIZED` are Spot only. The docs recommend `SPOT_PRICE_CAPACITY_OPTIMIZED` for most Spot use.**
- Location: AWS Batch User Guide, "Instance type allocation strategies for AWS Batch"
- Verdict: CARRIED (seed 03, re-fetched)
- Evidence: https://docs.aws.amazon.com/batch/latest/userguide/allocation-strategies.html | Tier 1, first-party docs | definition | BEST_FIT: "If additional instances of the selected instance type aren't available, AWS Batch waits for the additional instances to be available." and "This allocation strategy keeps costs lower but can limit scaling."; BEST_FIT_PROGRESSIVE: "If additional instances of the previously selected instance types aren't available, AWS Batch selects new instance types."; BEST_FIT_PROGRESSIVE_ORDERED: "AWS Batch selects instance types in the order they appear in the instanceTypes list." and "This strategy is only available for On-Demand Instance (EC2) compute resources."; SPOT_PRICE_CAPACITY_OPTIMIZED: "looks at both price and capacity to select the Spot Instance pools that are the least likely to be interrupted and have the lowest possible price"; "We recommend that you use SPOT_PRICE_CAPACITY_OPTIMIZED rather than SPOT_CAPACITY_OPTIMIZED in most instances."; SPOT_CAPACITY_OPTIMIZED_PRIORITIZED: "optimizes for capacity first, and honors instance type priorities on a best-effort basis" (accessed 2026-11-20)
- Use in dive: section 24, the allocation-strategy table. `[our reading]`: a Spot simulation farm lists several ray-tracing-capable families (F06-60) under `SPOT_PRICE_CAPACITY_OPTIMIZED`, or `SPOT_CAPACITY_OPTIMIZED_PRIORITIZED` to prefer the newest GPU.

**F09-5. An array job is one submission that spawns 2 to 10,000 child jobs sharing a job definition. Each child reads its index from `AWS_BATCH_JOB_ARRAY_INDEX` (starting at 0). The timeout applies per child; the parent has none. One failed child fails the parent once all children complete.**

### D. Batch schedulers on Kubernetes: Kueue, KAI Scheduler, Volcano (section 24)

Plain Kubernetes starts a pod as soon as a node fits it. A batch scheduler adds what shared GPU clusters need: a queue, quotas per team, borrowing of idle quota, preemption, and starting all pods of a multi-node job together or not at all (gang scheduling).

**F09-54. Kueue is at v0.20.7 (19 November 2026; v0.20.0 on 30 September 2026; v0.21.0-rc.0 is a pre-release). In its own words it "manages quotas and how jobs consume them": it decides when a job waits, when it is admitted (its pods may be created) and when it is preempted. It does not place pods on nodes and does not autoscale; those stay with kube-scheduler and the node autoscaler. From v0.20 it serves only the `v1beta2` API.**

### G. Capacity markets: how the instances are bought

A capacity market is the way an instance is paid for and what AWS promises in return. Five matter here: On-Demand (pay per second, no promise the instance is available when asked for), Spot (spare capacity at a discount, reclaimable on two minutes' notice), the On-Demand Capacity Reservation, ODCR (a held slot in one Availability Zone at the On-Demand price), the Capacity Block for ML (a prepaid GPU reservation with fixed start and end), and the SageMaker training plan (the same kind of block, sold for SageMaker targets, F09-34).

## 5. Decision path notes (for section 25, in place of teaching material)

This stream feeds no concept section, so there is no worked example on the arm. These notes give the section writer the order of questions and the evidence behind each fork. Every recommendation is `[our reading]`; the entry IDs carry the facts.

**Fork 0. Does the job need a scheduler at all?** One person at a simulation desktop is an instance with Amazon DCV and no queue (F09-104, F09-113). One eight-GPU node on a reservation for a fixed engagement was run by a named customer with no scheduler named (F09-88). Say this first, so the reader does not assume a cluster.

**Fork 1. How much does the team want to operate?** AWS's own rule: "Use the most managed option that supports the capabilities your workload needs" (F09-111). In order of rising ownership: SageMaker Training Jobs (nothing persists between runs, F09-81), AWS Batch (a queue and compute environments the team defines, instances come and go, F09-13), SageMaker HyperPod (a persistent cluster that AWS keeps healthy, F09-22 to F09-24), EKS run by the team (Karpenter or Auto Mode, F09-38, F09-48).

**Fork 2. Duty cycle: is the GPU busy most of the day?** Occasional jobs: pay per job (Training Jobs "no idle cost between experiments", F09-81; Batch scales to zero, F09-13). Back-to-back jobs: a warm fleet saves the start-up each time (the sample's reason for Batch, F09-73; "~5 min cold start" for a Training Job against an already-running HyperPod cluster, F09-83). Continuous, many teams: a persistent pool with quotas (HyperPod task governance on Kueue, F09-25, F09-26, F09-112). The cost of being wrong is visible in AWS's own example: four ml.g5.24xlarge held for 30 days is $29,374.40 whether jobs ran or not (F09-33).

**Fork 3. Coupling: do the parts of the job talk to each other while it runs?** Independent units (episodes, scenes, clips, checkpoints to evaluate): an array job of up to 10,000 children (F09-5) or a Distributed Map (F09-101), any instance size, any Zone. One node with several GPUs: still one job, no fabric. Several nodes exchanging gradients: EFA, one placement group or UltraCluster, one Zone (F09-8, F09-9, F09-36, F09-92), and a scheduler that starts all nodes together (Batch multi-node parallel jobs, F09-7; Kueue with the Kubeflow Training Operator on HyperPod, F09-81; Slurm, F09-87).

**Fork 4. Interruptibility: what is lost if the instance is taken away?** If the loss is one unit of at most 30 minutes, Spot with the `Host EC2*` retry is the documented pattern (F09-10, F09-11, F09-12). ## 7. Mental models worth teaching

1. **Five questions place a job: duty cycle, coupling, interruptibility, ray-tracing cores, reservation.** Duty cycle picks per-job billing against a held cluster (F09-81, F09-33). Coupling picks array fan-out against a gang-scheduled multi-node job on EFA (F09-5, F09-7, F09-9). Interruptibility picks Spot against On-Demand or reserved (F09-10, F09-95). Ray-tracing cores pick the G family (F06-60). Reservation picks Capacity Blocks or training plans, which exist only for P and Trainium (F09-91, F09-34). The first three are the same three properties register 08 uses to define its five shapes (F08-78).
2. **The GPU family decides the market before the orchestrator does.** P family: blocks and training plans, published prices, low Spot interruption in the data file. G family: no block, no plan, ODCR or On-Demand, noisy Spot in the busiest Region (F09-91, F09-35, F09-94, F09-96). A simulation fleet and a training fleet are bought differently even inside one cluster.
3. **An orchestrator is a queue plus a node lifecycle.** Batch owns both and removes nodes when the queue empties (F09-13). HyperPod owns node health and leaves the queue to Slurm or to Kueue (F09-22, F09-25). On EKS the two are separate products: Kueue or KAI for the queue, Karpenter or Auto Mode for nodes (F09-54, F09-57, F09-38, F09-48). OSMO sits above all of them as a workflow layer and still needs one of them underneath (F09-62).
4. **A persistent cluster is paid for by failures and by sharing.** HyperPod's case is node replacement, deep health checks and quotas across teams (F09-23, F09-24, F09-26); AWS's own posts say a one-shot fine-tune does not need it (F09-112, F09-81).
5. **Listing more than one instance type is the cheapest capacity tactic.** It works on On-Demand, needs no reservation, and appears in every orchestrator: Batch allocation strategies (F09-3), HyperPod flexible instance groups of up to 20 types (F09-29), Karpenter NodePools (F09-39, F09-86), the Training Jobs priority list (F09-82).
6. **A reservation fixes the shape of the job.** One Zone, a hard end time, no cancellation, no placement group, a single-use Batch compute environment (F09-90, F09-92, F09-17, F09-50). Plan the checkpoint before 11:00 UTC on the last day.
7. **Isolation and GPUs do not mix yet.** The new microVM pod sandbox is CPU only (F09-43, F09-45), so it fits the agent's code and tools, and the GPU job the agent launches runs outside it (F04-53).
8. **AWS publishes patterns, not a ranking.** Its physical AI material uses Training Jobs, Batch, HyperPod, EKS, ParallelCluster and bare reserved nodes for overlapping workloads (F09-80, F09-86 to F09-89), and no page comparing them was located (F09-110).
