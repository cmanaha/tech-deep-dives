Drift notes and replacement text:

1. Multi-rail handshake (:353-356). The page says "the sender picks a rail, sends a connection request carrying rail metadata, and the receiver confirms and binds that rail for the communicator. A rail is a software agreement between the two ends." The code does something else. The connect message carries the endpoint name of every rail (`include/nccl_ofi_rdma.h:624-636` struct with `num_rails` and `ep_names[MAX_NUM_RAILS]`, filled at `src/nccl_ofi_rdma.cpp:6189-6206`); the receiver rejects a mismatch in rail count (L4877-L4884) and inserts every remote rail into that rail's own address vector (L4681-L4700). Replacement:
   > Each rail gets its own `fi_endpoint`, Address Vector (`fi_av`) and Completion Queue (`fi_cq`). Setting up a communicator is a software handshake: the connect message carries the endpoint name of every rail, the receiver checks that both sides have the same rail count, and it inserts each remote rail into the matching local address vector. A communicator spans all of the rails in its group.
2. P2P GPU RDMA (:361-367). "Peer-to-peer access is a run-time property of a given pair of devices, so the plugin checks it per pointer and stages through host memory when it is unavailable." In code, GPU memory support is a per-device property set once and reported to NCCL: `props->hmem_support` follows the global `support_gdr` (`src/nccl_ofi_net.cpp:488-492`), and `ptrSupport` is `NCCL_PTR_HOST`, plus `NCCL_PTR_CUDA` only when `hmem_support` is true (`src/nccl_ofi_interface_nvidia.cpp:95-98`). Without it the plugin also forces NCCL's Simple protocol (`src/nccl_ofi_net.cpp:405-410`). The per-pointer call only finds which GPU owns a buffer. Replacement:
   > <strong>GPU memory support is decided once per device:</strong> the plugin asks libfabric whether the provider can register GPU memory and reports the answer to NCCL. When it can, the plugin advertises CUDA pointers alongside host pointers; when it cannot, it advertises host pointers only and forces the Simple protocol. The CUDA driver entry point it uses to find which GPU owns a buffer is resolved at load time rather than linked.
   (Cite nccl_ofi_net.cpp L405-L410 and L488-L492, nccl_ofi_interface_nvidia.cpp L95-L98, nccl_ofi_cuda.cpp L157 and L279-L297.)
3. sort_rails (:421-423). "reorders the NIC-to-GPU rail assignment itself" overstates it. The function reorders the EFA devices inside each GPU's group so that paired devices sharing Nitro card resources line up with the same index on the remote node, and only when a group has more than one device (L961-L991). Runtime topology discovery is a separate file: hwloc load at `src/nccl_ofi_topo.cpp:737`, XML written by `nccl_ofi_topo_write` at L1732. And on p4d, p4de and g5.48xlarge the plugin sets `NCCL_TOPO_FILE` to its own shipped file when the variable is unset (`src/platform-aws.cpp:661-687`). Replacement for :421-424:
   > On P5 and later the plugin builds the topology on the running instance <SourceRef code={nccl_ofi_topo.cpp L737}/> and reorders the EFA devices within each GPU's group so that paired devices line up across nodes <SourceRef code={platform-aws.cpp L961-L991}/>, so an unset variable is the correct setting there.
4. NCCL_TUNER_PLUGIN (:308-311). The sentence lists it under "Read against it" (the cheatsheet), which does not mention it. Two code facts exist at v1.20.0: the tuner lives in the network plugin library, and the plugin sets `NCCL_TUNER_PLUGIN` itself when it is unset, as a workaround for an NCCL reference-counting bug in the combined library "at least up to NCCL 2.27" (`src/platform-aws.cpp:500-532`). NcclOverEfa.tsx:499-502 and :663-667 already carry the NCCL 2.21 lookup-order claim. Replacement: drop the NCCL_TUNER_PLUGIN clause from the cheatsheet sentence and add one sentence: "Leave <code>NCCL_TUNER_PLUGIN</code> unset as well: the plugin sets it to its own library when it loads <SourceRef code={platform-aws.cpp L500-L532}/>."
