## ORCH-NOTES items

- **SBUF and PSUM cited to the NeuronCore-v3 page: FIXED.** This section names only SBUF; PSUM was cut by the author. The NeuronCore-v3 body says "on-chip SRAM is software-managed to maximize data locality" and never names SBUF. No page read says "no cache in front". The clause is now "the core's SBUF (State Buffer) scratchpad is software-managed: compiled code decides what sits there", citing `nkiTrnInf2Arch` then `neuronCoreV3`. The record matches src/sources/HeterogeneityFact.ts and src/sources/AwsCustomSilicon.ts: same key, title "AWS Neuron: NKI Trainium/Inferentia2 Architecture Guide", URL .../nki/guides/architecture/trainium_inferentia2_arch.html, tier 1 and accessed 2026-10-18. Source text: "two software-managed on-chip SRAMs, a 24MiB SBUF as the main data storage"; "state buffer (SBUF)". This matches the AwsCustomSilicon verifier's softening.
- **NIE proof wording: CONFIRMED, with two omissions FIXED.** The scope, the four properties, the assumptions and the micro-architectural exclusion all match the white paper (claims 10 to 15). The Alert also read as a complete list, but the white paper says the proof covers "the first three parts" of a five-part API. I/O device management and "Live update and live migration" are outside it. It also says "The current proofs use sequential reasoning and don't model concurrent execution across multiple physical CPUs". The Alert now names both (claim 11b). **Determinism:** the section does not claim determinism by construction for the NEFF. The only related clause is "fixes memory allocation and instruction order at compile time" (nkiOverview: "memory allocation and instruction scheduling are done in this stage") plus a cross-reference by name to *Determinism: NEFF and GPU Reproducibility*.
- **MIG profiles: H100, H200 and B200 CONFIRMED; B300 WRONG, fixed.** Every H100 (80 GB), H200 (141 GB), B200 (180 GB), A100 and GB300 (DGX Station) row matches the MIG user guide's Supported MIG Profiles tables (claims 22 to 27). B300: the Blackwell Ultra blog does state "seven instances with 34 GB each", but for "Blackwell Ultra GPUs", with no product named. The MIG user guide has no B300 row on any page. NVIDIA's MIG product page has a "MIG Specifications" table: GB300 NVL72 "7x 34 GB / 4x 69 GB / 2x 139 GB / 1x 279 GB"; HGX B300 "7x 32 GB / 4x 67 GB / 2x 135 GB / 1x 270 GB" ("Preliminary specifications"). So the "B300" label was wrong for an HGX B300 (P6-B300) reader, and "no published ... whole-GPU profile" was contradicted. The row is now "Blackwell Ultra, 288 GB (NVIDIA blog example)". The paragraph below says the MIG page gives that split to GB300 NVL72 and lists HGX B300 as 7 x 32, 4 x 67, 2 x 135 or 1 x 270 GB, citing the new `migProductPage` record (T2).
- **Confidential computing: CONFIRMED against the cited pages, conflict FIXED.** TEE-I/O and inline NVLink protection are confirmed on the Blackwell Ultra blog. WP-12554 v1.3 confirms single-GPU and multi-GPU pass-through, up to eight on Blackwell with NVLink encrypted, "The GPUs are not shared among VMs", CPU-to-GPU encryption, and "AMD SEV-SNP or Intel-TDX". NVIDIA's MIG product page says the opposite: Blackwell and Hopper are "securely isolating each instance with confidential computing". The expandable now says "In the confidential-computing modes NVIDIA documents" and adds "NVIDIA's MIG page says confidential computing isolates each MIG instance [vendor-claim]; the white paper lists only whole-GPU modes". [SECONDARY: WebSearch summary] NVIDIA's CC deployment guide v7.1 (April 2026) also lists only single-GPU and multi-GPU Blackwell modes. I did not fetch it, so it is not cited.
