## 1. Hardware, device side: what one drive delivers

**Summary.** Two device classes now matter. (a) Mainstream TLC data-center NVMe on PCIe Gen5 and Gen6: about 14 GB/s (Gen5) and 28 GB/s (Gen6) sequential read per drive, 3 to 7 million 4 KiB random-read IOPS, and about 60 µs typical QD1 read latency. (b) "Super high IOPS" drives built for GPU-initiated access at 512-byte granularity, led by NVIDIA's Storage-Next initiative: Kioxia GP1 (XL-FLASH, 10 million 512 B IOPS, samples by end of 2026) and SK hynix AIN P (samples by end of 2026), with 100 million IOPS on the roadmap. The useful mental model: at 4 KiB a Gen6 drive is close to bandwidth-bound (5.5 M x 4 KiB = 22.5 GB/s of a 28 GB/s drive); at 512 B the same link would need about 60 million IOPS to fill, which is why the new drives chase IOPS rather than GB/s **[derived]**. KV cache pages are far larger than 512 B (Topic 6d), so for KV offload the drive's GB/s is the number that matters, and 512 B IOPS matter for embeddings, vector search and GNN feature lookups.

**Practical reading.** A Gen6 TLC drive gives about 2x a Gen5 drive in sequential read (28 vs 14 GB/s). The 512 B SCM-class drives (GP1, AIN P) are sampling at the end of 2026 and are not a buy-today option.

## 2. Hardware, data path: who moves the bytes between flash and HBM

**Summary.** There are three generations of data path, and the right one depends on transfer size. (1) **CPU bounce**: NVMe to host DRAM to HBM, two copies, CPU in both the control and data path. (2) **GPUDirect Storage (GDS, cuFile)**: the CPU still issues the I/O (control path), but the DMA lands directly in HBM, skipping the bounce buffer. (3) **GPU-initiated I/O (BaM research, productised as NVIDIA SCADA)**: GPU threads build NVMe commands, ring doorbells and poll completions themselves, so both control and data path leave the CPU. The BaM paper (author-measured) shows why the third exists: CPU-initiated GDS only fills a PCIe Gen4 x16 link at 32 KiB and larger I/Os and reaches 23.6% of it at 4 KiB, while GPU-initiated I/O fills it at 4 KiB. A KV block for a whole layer stack is hundreds of KiB to MiB (Topic 6d), so KV offload sits in the range where GDS or even a CPU bounce is adequate; GPU-initiated I/O pays off when the granularity drops to a few KiB or 512 B. In parallel, NVIDIA moved the shared flash tier off the GPU server entirely: the BlueField-4-based CMX platform (announced at CES 2026 as "Inference Context Memory Storage") is an Ethernet-attached flash tier for KV cache, labelled G3.5 between node-local SSD (G3) and shared storage (G4). CXL hybrid flash (Samsung CMM-H) is a fourth, CPU-side option; its only public measurements are of an FPGA prototype.

## 3. Platform side: serving stacks with a tier that spills to flash

**Summary.** Every major open serving stack now has a KV hierarchy whose third tier is flash, and they converge on the same shape: GPU HBM, then a private pinned host-DRAM tier, then a disk or shared-storage tier, with a router that knows which worker holds which prefix in which tier. NVIDIA Dynamo's KV Block Manager names the tiers G1 (GPU), G2 (pinned host), G3 (disk), G4 (object storage); SGLang HiCache calls them L1, L2, L3 and stresses that only L3 can be shared across instances; vLLM's native `OffloadingConnector` gained a filesystem tier; llm-d packages all of them for Kubernetes. Two design choices matter for flash: (1) **admission to disk is filtered**, because writing every evicted block burns drive endurance and bandwidth for blocks that are never read again (Dynamo's default filter writes a block to disk only on its second sighting within a ten-minute decay window, read from the code); (2) **the router discounts lower tiers**: Dynamo credits a host-tier hit at 0.75 and a disk-tier hit at 0.25 of a GPU hit by default. Published production evidence is thin but consistent: Mooncake (Kimi) reports that local DRAM alone reaches only about half of the theoretical hit rate and that its pooled DRAM+SSD cache let Kimi handle 75% to 115% more requests; DeepSeek serves its public API from a disk-backed context cache and prices cache-hit input at 1/30 to 1/50 of cache-miss input.

## 4. Storage vendors positioning flash as context memory

**Summary.** Every large file and object storage vendor now sells a "KV cache" or "context memory" story, and every headline number located in this research is a VENDOR CLAIM measured against a recompute or HBM-only baseline. The numbers cluster where the physics says they should: a 100K-plus-token prefix that takes tens of seconds to recompute loads in 2 to 3 seconds over a 200 Gb/s-class link, so 20x to 27x TTFT claims follow from the long-context setups chosen, not from anything unique to one product **[derived]** (Topic 6a). Prefill FLOPs for a prefix of p tokens = 2 x N_active x p (all weight matmuls; this slightly overstates Llama 70B because embeddings cost no matmul) + l x n_heads x (d_qk + d_v) x p^2 (causal attention: QK^T and AV, about p^2/2 query-key pairs, 2 FLOPs per multiply-add). - A2. Node = 8 GPUs serving one model replica (tensor parallel 8). Node compute G = 8 x dense peak: H100/H200 989.5 TFLOPS BF16 or 1,979 TFLOPS FP8 per GPU [W: 05-workloads.md ridge table, from nvidia.com H100/H200 pages]; B200 4.5 PFLOPS FP8 dense per GPU [W: same table, DGX B200 page]. Break-even figures use 100% of peak, which makes recompute look as cheap as it can; at a realistic prefill MFU the recompute takes longer and the break-even bandwidth falls in proportion (at 50% MFU, halve every B* below). The MFU itself is not measured here.
- A3. Fetch is not overlapped with compute (worst case for fetch). Layer-by-layer pipelining, which LMCache, KVBM and Mooncake all do, hides part of the fetch.
- A4. KV bytes per token from `01-memory.md` (BF16/FP16 unless stated): Llama 3.1 70B 327,680 B; Qwen3-235B-A22B 192,512 B; DeepSeek-V3 70,272 B (MLA latent plus RoPE key); DeepSeek-V4.1-Flash 890 B [M:T1-32], [M:T1-33], [M:T1-36], [M:T1-43]. ### 6a. Recompute cost vs fetch cost

The break-even tier bandwidth for a node is B* = (KV bytes per token) x G / (prefill FLOPs per token). Fetching from a tier with bandwidth above B* is faster than recomputing. Two things fall out of the formula: B* scales with the ratio of KV bytes per token to active parameters (a model property), and B* falls as the prefix grows, because attention FLOPs grow with p^2 while KV bytes grow with p.

## 7. Flash cache tier vs High Bandwidth Flash (one paragraph)

Rows prefixed `H:` reuse the High Bandwidth Flash register `hbf.md` (accessed 2026-10-17, not re-fetched here); its source IDs keep their own numbering.

Both tiers are NAND, and they sit on opposite sides of the accelerator package edge, which sets the job each one fits. A flash cache tier is off-package, behind PCIe or the network: on an 8-GPU AWS instance it gives about 2 to 19 GB/s per GPU and 3.8 TB per GPU locally (unbounded when shared), and it ships today. Its job is capacity for KV prefixes that are written once and read on each later hit, and section 6a shows that job needs only 2 to 20 GB/s per GPU on Hopper to beat recompute. High Bandwidth Flash (HBF) is stacked NAND on the package beside HBM: the OCP specification v0.7.0 (2026-08-03) fixes 512 GiB per 16-high stack and 0.384 to 3.072 TB/s per stack, Sandisk's first product claims 1.6 TB/s, and samples are a roadmap item (Sandisk and SK hynix targeted memory samples in the second half of 2026). That is about 700x the per-GPU bandwidth of the instance store, aimed at data read on every decode step. The HBF sources place frozen weights (MoE expert pools first) and slow-changing shared context on it and keep per-token KV off it, because per-token writes collide with NAND endurance and the spec's host-managed refresh. A reader can hold the two as one rule: HBF serves bytes read every step, a flash cache tier serves bytes read once per hit **[derived]**.

## Author guidance

**Strongest mental model, in one line.** Reading a prefix's KV from a tier beats recomputing it once the tier delivers more than GPU FLOPS x KV bytes per token / prefill FLOPs per token, which for a dense 70B model on an 8x H100 node is about 17 GB/s per node (about 2 GB/s per GPU) even at peak compute, so the flash already in every P5 and P6 is fast enough, and what flash adds is memory time: about an hour of a busy node's prefixes against about 100 seconds in HBM **[derived]** (M1, M7, R2).

**Actionable facts (3 to 5).**
1. Every 8-GPU P5, P5e, P5en, P6-B200 and P6-B300 instance carries 8 x 3,800 GB of NVMe instance store (30.4 TB, 4.4 M random-read IOPS at 4 KiB), already paid for and wiped at stop, which suits KV because KV can be recomputed **[SPEC, T1-19]** (A1, A2). AWS publishes no large-I/O GB/s for it; the IOPS imply at least 18 GB/s per instance **[derived]** (A10).
2. Build the hierarchy in order: host DRAM tier first, sized larger than the GPU KV pool, then disk sized at least as large as the host tier (`DYN_KVBM_CPU_CACHE_GB`, `DYN_KVBM_DISK_CACHE_GB`), with a disk admission filter on: Dynamo's default writes a block to disk only on its second sighting within a 600 s decay window **[VENDOR CLAIM guidance, T1-7; SPEC code, T1-8]** (S3, S5).
3. Keep KV off EBS: the per-instance EBS cap (12,500 MB/s on p5en and P6) is below the instance-store floor, and below the 17 GB/s break-even for a dense 70B on Hopper **[SPEC, T1-19; derived]** (A11, M1).
4. For a cache shared across nodes, FSx for Lustre with EFA and GDS is the AWS-documented path to 1,200 Gb/s (150 GB/s) into one P5 to P6-B300 client; Trn2 is excluded as an FSx EFA client; size throughput, not TiB (about 150 TiB of PERSISTENT-1000 to feed one client at full rate) **[SPEC, T1-20, T1-21, T1-22; derived]** (A14 to A18).
5. Watch load bytes against store bytes (`vllm:kv_offload_load_bytes` vs `vllm:kv_offload_store_bytes`) and the external prefix-cache hit rate; a tier written far more than it is read spends drive endurance (a 1 DWPD 30.72 TB drive absorbs about 356 MB/s for five years) for no TTFT gain **[SPEC code, T1-13; derived, T1-1]** (S16, D23).

**Suggested h2 headings, each with its payoff.**
1. "When reading KV beats recomputing it": one ratio and one number (17 GB/s per 8x H100 node for a dense 70B) tell you whether any tier is fast enough before you buy it.
2. "How long each tier remembers": HBM holds about 100 seconds of a busy node's prefixes and local flash about an hour, so you can match the tier to the gap between a user's turns or an agent's tool calls.
3. "The flash you already pay for on P5 and P6": 30.4 TB per instance, what it delivers, and the knob in Dynamo, SGLang, vLLM or LMCache that turns it into a KV tier.
4. "Sharing context across nodes": when FSx for Lustre with GDS, a storage vendor's KV store or HyperPod's managed tier is the next step, and how to read a vendor's 20x TTFT claim (V5, V7: the arithmetic predicts it).
5. "Who moves the bytes": why KV offload is a GB/s problem served by GDS or a host bounce, and where 512-byte drives and GPU-initiated I/O fit.
6. "Flash on the package": one paragraph on High Bandwidth Flash, which serves bytes read every step, against a flash cache tier, which serves bytes read once per hit.
7. Close on the order of operations from fact 2 (host tier, then local flash with an admission filter, then shared flash), so the section ends on what to configure.
